# Lane Pins Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A PIN key for each part (chords, bass, melody), so that sprinkle and the feel knobs only rewrite the parts that are not pinned.

**Architecture:** The engine gains one entry point that generates an idea while keeping the pinned lanes of a previous idea.
The plugin passes the previous idea and three new pin parameters to it on every regeneration.
It also saves the whole current idea in its state, so a reload gives back exactly what the owner heard.
The editor gets three PIN keys whose layout the owner picks from a mockup.

**Tech Stack:** C++20, JUCE 9.0.4, Catch2, CMake presets `dev`/`asan`/`tsan`/`lint`.

**Spec:** `docs/spec/magic-dust-spec.md`, the section "Pin, reroll and seeds" and the controls table.
This plan brings lane pins forward from Phase 5, on the owner's request of 2026-10-28.
Chord-cell pins, reroll and swap stay in Phase 5.

## Global Constraints

- The parameters are `chordsPin`, `bassPin` and `melodyPin`, `AudioParameterBool`, default false, `ParameterID{id, 1}`, with the titles "chords pin", "bass pin" and "melody pin".
- Pins hold through:
  - sprinkle
  - mood, energy, flavour and groove changes
  - style changes
- A key change transposes the pinned lanes to the new key, as described below.
- With nothing pinned, every regeneration is byte-identical to today, so the goldens do not change.
- Never allocate, lock or block on the audio thread. Regeneration already runs on the message thread.
- **Docs:** no em dash, and long Markdown has one sentence per line.
- **Commits:** never add Co-Authored-By or an agent name.
- Before each commit, the dev tests, lint and format must pass.

## Musical rules

- **Chords pinned:** the progression, its entry, the parallel flag and the chord lane events stay.
  Unpinned bass and melody are generated fresh, from their new lane seeds, against the kept chords.
  The bass pattern is drawn from the kept entry.
- **Bass pinned and chords not pinned:** the bass events stay, and `refitBass` fits them to the new chords.
- **Melody pinned and chords not pinned:** the melody events stay, and a new `refitMelody` fits them to the new chords.
- **Everything pinned:** sprinkle changes nothing and the idea number does not change.
- **Key change while anything is pinned:**
  - Each pinned lane and the kept progression move by the interval from the old root to the new root, taken in -5 to +6 semitones.
  - A note that leaves its lane's range moves by an octave back into range.
  - The pinned bass and melody are then refitted if they fail validation.
- **Bar-count change:** a change to the bar count ignores pins, because the kept lanes would not fit.
- **Refit badge:** a refitted lane keeps `refitted` set. The badge itself stays in Phase 5.

## Review Focus

1. **Pinned bass survives three sprinkles in a row.** Each sprinkle refits from the bass as last refitted, not from the original. The result stays valid and keeps the starts. Task 1 tests this.
2. **Chords pinned, then a flavour change.** The chords must not change, even though flavour normally rewrites chords. Task 1 tests this.
3. **Reload after a refit.** The saved idea gives back the refitted notes, not a regeneration from seeds. Task 2 tests this.
4. **A pinned lane that is also muted.** Mute and pin are independent. A muted pinned lane stays pinned and silent. Task 2 tests this.
5. **A sender while the main's lane is pinned.** The sender sends the pinned notes, with no change needed. Task 2 checks this with the existing Link test.

### Task 1: Engine - generate while keeping pinned lanes, and refit the melody

**Files:**
- Modify: `engine/include/md/generate.hpp`, `engine/src/generate.cpp`, `engine/src/refit.cpp`
- Test: `tests/engine/test_pins.cpp` (new, with its CMake entry), `tests/engine/test_refit.cpp`

**Interfaces:**
- Produces:
  - `struct Pins { bool chords = false; bool bass = false; bool melody = false; };`
  - `Idea generate(const Bank&, const Settings&, std::uint32_t seed, const LaneSeeds&, const Idea& previous, Pins pins);`
  - `bool refitMelody(Idea& idea);`
- When `pins` is all false, or `previous.settings.bars != settings.bars`, the new overload returns exactly what `generate(bank, settings, seed, laneSeeds)` returns.
- Every result passes `validate`.

- [ ] **Step 1: Write the failing tests in `test_pins.cpp`.**
  - **No pins:** with no pins, the new overload equals the old one, byte for byte, over 50 seeds.
  - **Chords pinned across sprinkle:** with chords pinned and a new seed and lane seeds, the progression and chord events are identical. Bass and melody differ for at least 45 of 50 seeds, and the result validates.
  - **Chords pinned across flavour:** with chords pinned, a flavour change from soulful to jazzy keeps the chords identical.
  - **Bass pinned:** with bass pinned and a new seed, the bass starts and lengths are identical, the result validates, and `refitted` is true whenever a pitch changed.
  - **Bass pinned, three sprinkles:** with bass pinned through three sprinkles in a row, each feeding the last result back in as `previous`, the starts stay identical and every result validates.
  - **Melody pinned:** the same as the bass case, for the melody.
  - **Everything pinned:** the result equals `previous` in progression and all three lanes.
  - **Key change:** with chords and bass pinned and the key moving from A to C, the chords move up 3 semitones. The bass is in range and the result validates.
  - **Bar count change:** with a different bar count, the pins are ignored.
- [ ] **Step 2: Write the failing `refitMelody` tests in `test_refit.cpp`.**
  - A valid melody is unchanged and `refitted` stays false.
  - A melody under foreign chords comes out valid, with identical starts, lengths and velocities.
  - The refit is deterministic.
- [ ] **Step 3: Run the tests and watch them fail.**
- [ ] **Step 4: Implement the overload in `generate.cpp`.**
  - Reuse the existing build steps. When chords are pinned, skip the entry, progression and chord build, and copy them from `previous`, transposed for a key change.
  - Then build each unpinned lane as today.
  - Then copy each pinned lane, transposed, and refit it.
  - The existing `generate` path must stay byte-identical.
- [ ] **Step 5: Implement `refitMelody`.**
  - Walk the notes in start order.
  - Snap each failing note to the nearest pitch that passes all the melody rules, given the previous already-fitted note. A chord tone of the sounding chord comes first, then a scale tone, ties going down, in range.
  - Never move a start, length or velocity. Share the validator's per-note predicates instead of copying them.
- [ ] **Step 6: Run the dev suite, lint and format, then commit** with the message `feat(engine): generate keeping pinned lanes, and refit a pinned melody`.

### Task 2: Plugin - pin parameters, regeneration and saved idea

**Files:**
- Modify: `plugin/PluginProcessor.h`, `plugin/PluginProcessor.cpp`
- Create: `plugin/IdeaState.h/.cpp`, which converts an Idea to and from a `juce::ValueTree`
- Test: `tests/plugin/test_processor.cpp` or the nearest existing processor test, and `tests/plugin/test_idea_state.cpp`

**Interfaces:**
- Consumes: the Task 1 `Pins` and the new `generate` overload.
- Produces:
  - `md::Pins MagicDustProcessor::pins() const`, which reads the three parameters
  - `juce::ValueTree ideaToTree(const md::Idea&)` and `std::optional<md::Idea> ideaFromTree(const juce::ValueTree&)`

- [ ] **Step 1: Write the failing tests.**
  - **Bass pinned, sprinkle:** with `bassPin` set, a sprinkle keeps the bass starts and changes the chords for at least 9 of 10 sprinkles.
  - **Chords pinned, mood change:** with `chordsPin` set, a mood change followed by the 150 ms quiet regeneration keeps the chords.
  - **Save and load:** state saved after a refit loads back to an identical idea, every lane and the progression.
  - **Fallback:** a state with no idea child, which is today's format, or a corrupt idea child loads from the seeds as today.
  - **Mute and pin:** a pinned lane that is also muted stays pinned and is silent.
  - **Senders:** the existing sender test still sends the main's current, pinned notes.
  - **Round trip:** `ideaToTree` then `ideaFromTree` returns an equal idea for 50 generated ideas.
- [ ] **Step 2: Run the tests and watch them fail.**
- [ ] **Step 3: Implement.**
  - Add the three parameters next to the mute parameters.
  - Make every regenerate path use the new overload, passing `*idea_` as `previous` when an idea exists. This covers sprinkle, the feel knobs, groove, style and key.
  - Save `ideaToTree(*idea_)` as a child of the main's state.
  - On load, use the saved idea only when it parses and passes `validate`. Otherwise regenerate from the seeds as today.
  - Bump `schemaVersion` only if the existing load code needs it to tell formats apart. The fallback must accept both.
- [ ] **Step 4: Run the dev suite, the plugin tests, lint and format, then commit** with the message `feat(plugin): pin parameters keep lanes through regeneration, and the idea is saved`.

### Task 3: Editor - PIN keys

**Files:** `plugin/PluginEditor.h/.cpp`, `ui/Tokens.h`, `ui/KeyButton.*` (only if a key needs a lane-coloured LED), `tests/plugin/test_editor.cpp`

The layout is the one the owner picks from `docs/spec/visual/pin-keys-mockup.html`.
The brief for this task is written after that choice and is added to this plan before Task 3 starts.
Whatever the layout:
- **The key:** each PIN key toggles its pin parameter through a `ButtonParameterAttachment`.
- **The LED:** the key's LED lights in the lane's cap colour, from the visual spec, while that part is pinned: `cap-chords` `#7B6BD6`, `cap-bass` `#D6527C`, `cap-melody` `#3FB6C4`.
- **The display:** a pinned lane's row shows a small "PINNED" tag, and its row label is not dimmed.
- **Accessibility:** the keys have the titles "pin chords", "pin bass" and "pin melody". They can take focus, and Enter presses them. The focus order puts each lane's pin key after its octave keys.
- **Renders:** re-render editor-100, editor-200 and about-100 with bass pinned, and check them pixel by pixel.
- [ ] Write the tests: the attachment toggles the parameter, the LED follows the parameter, and the focus order is correct.
- [ ] Implement, render, look, and commit with the message `feat(ui): pin keys for chords, bass and melody`.
